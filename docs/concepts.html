The thinking happens on the server. The work happens on runners, on machines you choose. You look in through any client, from any device. Six words name everything else.

This page is our scratchpad: what's settled, what's open, and where we are. It changes as we decide.

The words

One word per thing. The test for a word: it names something you can point at in the code or the API, and nothing else in the list overlaps it. Under each, the words people reach for instead, and what they map to here.

Server built
The one process you start, bun server.js, on any box you own. It keeps every thread and every agent's conversation in one SQLite file, and Pi Durable makes sure a restart or a stop loses and repeats nothing. What you might call a workspace, or the cloud. A server is the workspace: one server is one world; run another for another.
Runner built
A program on a machine that lends the server two things: a folder and the model logins pi has there. Started by hand, or installed with one line, curl -fsSL <server>/runner.sh | sh, after which it keeps itself up to date. It can be read-only, and it can have an owner. What you might call a machine, a computer or a daemon. The machine is only where a runner runs, a laptop, a VPS or a container, and one machine can run several runners: one per folder, or one read-only next to one that writes. A computer, elsewhere, bundles where files are, where commands run and which provider made the box; here a cloud sandbox is just a machine you run the curl line on. The daemon is the runner.
Agent built
A model, how hard it thinks, and the runner it runs on: sonnet:high@laptop. In each thread an agent has its own conversation. It is handed messages, posts only its final answer, and can read any agent's work: the tool calls it made and what they printed. It knows its folder the way pi does there: AGENTS.md and skills. Not a bot. An agent has no name of its own and no character; it is "this model, this hard, there".
Thread built
A conversation on the server, with any number of people and agents in it. A message asks the agents in its to, or whoever the thread asked last. Threads fork at any entry, and talk to each other: a child's answer comes back to its parent exactly once. Threads don't live on runners. A thread can ask an agent on the laptop and one on the vps side by side.
Client built
Whatever you look through: the web client in any browser, the CLI in a terminal, a Matrix room. They all speak the same small HTTP and WebSocket API, and none of them stores anything. What you might call the desktop or the mobile app. A desktop app would be a window, a server and a runner in one program; here that's RUNNER=~/code bun server.js and a browser tab, each part visible. On your phone it's the web client over Tailscale, never the open internet, since whoever can reach the server can use it: tailscale serve --bg --https=443 http://127.0.0.1:3000.
Bot later
A who: a name and instructions, running as some agent. ada might be sonnet:high@laptop plus her character; move her to the vps and she's still ada. It belongs on the server, because it's part of the thinking, not the doing. Waits until everything above is rock solid.

How an agent is named

sonnetmodel:highthinking@laptoprunner

Each part is optional and falls back to pi's defaults on that runner: laptop alone is its default model. The model part is anything pi --model takes, resolved by pi on the runner.

The brain never leaves the server: the agent's loop, its conversation and its memory. The runner is its hands and its voice: it runs the tools, and it carries the model calls on its own logins. If the runner drops mid-way, the agent waits for it and carries on.

A runner's life

stateDiagram-v2
  direction LR
  [*] --> Online: curl …/runner.sh | sh
  Online --> Offline: machine sleeps, network drops
  Offline --> Online: dials back by itself
  Online --> Updating: new runner on the server, and it's idle
  Updating --> Online: fetched, installed, restarted

The server ships its own runner, so a runner always matches its server. It never updates mid-answer: the server asks only when it has nothing open.

Who pays: the runner

An agent's model calls go out through the pi logins on its runner, so whoever lends a runner pays for the thinking on it. agent-ide is for one person and for teams alike, and this answer holds for both.

flowchart LR
  subgraph yours["Your runner pays for your agents"]
    a1["sonnet@laptop"] -- "thinks with" --> l1["the laptop's login"]
    a1 -- "works in" --> f1["the laptop's ~/code"]
  end
  subgraph pool["A shared pool is a runner without an owner"]
    a2["anyone's agent @pool"] -- "thinks with" --> l2["a key in that machine's environment"]
    a2 -- "works in" --> f2["its folder"]
  end
  • Just you: every runner is yours, with your logins. Nothing to decide.
  • A team: Ana's runners pay for the agents on them, and --owner and --allow say who else may use them. Nobody's subscription quietly becomes everyone's, and someone who leaves takes their logins along by stopping their runner.
  • A pool, if a team wants one: a runner without an owner, next to the server, with a key in its environment. pi's enabled models there are the list, and pi's default there is the default.
  • The server holds no secrets. Keys kept on the server would be pooled: one key, everyone spending it, and no way to say whose share was whose.

Two costs we accept. A machine with no login can't think: give it a key in its environment. And someone has to run pi and /login on a machine once, rather than signing in from the web client. If thinking on the laptop while working on the vps is ever needed, it's one optional field on an agent.

The whole picture lives in the thread

Settled: answer 2, below, and built. threads {thread, agent} reads an agent's work in a thread. Any agent may read any agent's work, as any person can already through the API.

We first asked whether an agent should have one runner or several. That asks about reach, and reach is mostly solved: on your machines an agent's bash can already ssh vps tail /var/log/site.log; the runner fences its file tools, not ssh. Take a task that spans machines: the site on the vps throws errors, and the code behind them is on the laptop. What hurts when two agents share it is that each sees only what the other says, never what it saw.

So the question is where the whole picture lives. Three answers:

1. In one agent

One agent reaches every machine, through several runners or through ssh. It sees everything, in one long conversation, and the hops between machines hide inside its tool calls.

2. In the thread

An agent on each machine, as today, and one tool that reads any thread and any agent's work in it: not only what an agent said, but the tool calls it made and what they printed, word for word.

sequenceDiagram
  participant You
  participant L as sonnet@laptop
  participant V as sonnet@vps, in a child thread
  You->>L: the site throws 500s, fix it
  L->>V: post: what's failing on the vps?
  V->>V: bash: tail the log, curl the health check
  V-->>L: a null user in /api/me
  L->>V: threads: read sonnet@vps's work
  V-->>L: its calls and their output, word for word
  L->>L: edit and test, in ~/code
  L-->>You: fixed, and why

3. In you

You ask the vps agent and the laptop agent in one thread, and carry what one found to the other. It works today, with no design at all, and it's you doing the work.

The tool

The threads tool, from talk.js, already read any thread's messages. It gained one argument: threads {thread, agent} reads that agent's tool calls and what they printed, with query and last to narrow it. Three things it decided:

  • A principle changes. "Agents only see messages" becomes "agents are handed messages, and can look up anything". What they're handed stays small; what they can find is everything.
  • Whose work an agent may read. Anyone's. Every person who can reach the server can already read every conversation, so a fence for agents alone would guard nothing. If a server ever has accounts, both get the same fence.
  • Size. Tool output can be huge. For now a line is cut at 4,000 characters, saying how much is left, and query finds the part that matters. Real paging can come when a task needs it.

So: the thread. Each agent keeps one runner, every hop stays a message you can read, the split knowledge goes, and it was a small change to a tool we already had. One runner or several stopped being a question: one, and ssh for whoever wants more.

Where we are

  • A server that survives restarts and stops, on Pi Durable.
  • Runners: started by hand or with one curl line, self-updating, read-only if you like, with owners.
  • Agents as model:thinking@runner, knowing their folder's AGENTS.md and skills.
  • Threads with many people and agents, forks, and threads that talk to each other.
  • Clients: the web client, the CLI, Matrix.
  • Agents read each other's work, so work across machines stays in the thread.
  • Web search, as a module: the simplest that works, to show how a tool plugs in.
  • Bots, once the rest is rock solid.
  • Memory, a thread that never has to end, still being explored.
  • A desktop app, a phone app, cloud machine kinds, accounts. Each is a shell around what's already here.

What agent-ide is made of

The thinking happens on the server. The work happens on runners, on machines you choose. You look in through any client, from any device. Six words name everything else.

Everything that must survive lives in the middle box. A runner or a client can vanish at any moment and nothing is lost: threads wait for a runner to come back.

The words

One word per thing. The test for a word: it names something you can point at in the code or the API, and nothing else in the list overlaps it.

Server built
The one process you start, bun server.js, on any box you own. It keeps every thread and every agent's conversation in one SQLite file, and Pi Durable makes sure a restart or a stop loses and repeats nothing. Not a "workspace" and not "the cloud". One server is one world; run another for another.
Runner built
A program on a machine that lends the server two things: a folder and the model logins pi has there. Started by hand, or installed with one line, curl -fsSL <server>/runner.sh | sh, after which it keeps itself up to date. It can be read-only, and it can have an owner. Not a "computer", not a "daemon". One machine can run several runners: one per folder, or one read-only next to one that can write.
Agent built
A model, how hard it thinks, and the runner it runs on: sonnet:high@laptop. In each thread an agent has its own conversation, sees only messages, and posts only its final answer. It knows its folder the way pi does there: AGENTS.md and skills. Not a bot. An agent has no name of its own and no character; it is "this model, this hard, there".
Thread built
A conversation on the server, with any number of people and agents in it. A message asks the agents in its to, or whoever the thread asked last. Threads fork at any entry, and talk to each other: a child's answer comes back to its parent exactly once. Threads don't live on runners. A thread can ask an agent on the laptop and one on the vps side by side.
Client built
Whatever you look through: the web client in any browser, the CLI in a terminal, a Matrix room. They all speak the same small HTTP and WebSocket API, and none of them stores anything. This is where "desktop" and "mobile" go: they are screens, not parts of the system.
Bot later
A who: a name and instructions, running as some agent. ada might be sonnet:high@laptop plus her character; move her to the vps and she's still ada. It belongs on the server, because it's part of the thinking, not the doing. Waits until everything above is rock solid.

How an agent is named

sonnetmodel:highthinking@laptoprunner

Each part is optional and falls back to pi's defaults on that runner: laptop alone is its default model. The model part is anything pi --model takes, resolved by pi on the runner.

One message, start to finish

sequenceDiagram
  participant You as You, in any client
  participant T as Thread, on the server
  participant A as The agent, on the server
  participant R as runner laptop
  participant M as The model's provider
  You->>T: "fix the flaky test", to sonnet:high@laptop
  T->>A: everything it hasn't seen yet, as one input
  A->>R: model request
  R->>M: with the laptop's login
  M-->>A: streamed back: call bash
  A->>R: bash: bun test, in ~/code
  R-->>A: what it printed
  A->>R: model request, and so on
  A-->>T: only its final answer
  T-->>You: live, as it lands

The brain never leaves the server: the agent's loop, its conversation and its memory. The runner is its hands and its voice: it runs the tools, and it carries the model calls on its own logins. If the runner drops mid-way, the agent waits for it and carries on.

A runner's life

stateDiagram-v2
  direction LR
  [*] --> Online: curl …/runner.sh | sh
  Online --> Offline: machine sleeps, network drops
  Offline --> Online: dials back by itself
  Online --> Updating: new runner on the server, and it's idle
  Updating --> Online: fetched, installed, restarted

The server ships its own runner, so a runner always matches its server. It never updates mid-answer: the server asks only when it has nothing open.

Words we don't use, and why

Machine
Plain English for where a runner runs: a laptop, a VPS, a container. It isn't a concept in agent-ide; the runner records its host, and that's all.
Computer
do-computer's word for where a Dood works, which bundles three ideas: where the files are, where commands run, and which provider made the box (a virtual shell, Daytona, Modal, Cloudflare, or your own paired machine). agent-ide has one kind: anywhere you can run the curl line. A cloud sandbox is just a machine you run it on.
Daemon
The runner is the daemon. One word is enough.
Desktop
do-computer's desktop app is three things in one program: a window, a server, and a daemon. agent-ide gets the same with RUNNER=~/code bun server.js and a browser tab, and you can see each part running.
Mobile
The web client in your phone's browser. Reach the server over Tailscale, never the open internet: there are no accounts, so whoever can reach it can use it.
Workspace
A server is the workspace. Who may use a runner is the runner's owner's call.

Next to do-computer

do-computer is a good neighbour to think against: the same idea, a product around it. Where we differ, it's on purpose.

do-computer's hardest-won idea is that the agent has no computer of its own. We agree, and go one further: it doesn't choose one either. Choosing is a person's job, done once, in the agent's name.

Where we are

  • A server that survives restarts and stops, on Pi Durable.
  • Runners: started by hand or with one curl line, self-updating, read-only if you like, with owners.
  • Agents as model:thinking@runner, knowing their folder's AGENTS.md and skills.
  • Threads with many people and agents, forks, and threads that talk to each other.
  • Clients: the web client, the CLI, Matrix.
  • Bots, once the rest is rock solid.
  • Memory, a thread that never has to end, still being explored.
  • A desktop app, a phone app, cloud machine kinds, accounts. Each is a shell around what's already here.

What it promises

  1. Threads with many authors. Humans and agents talk in one thread, and each agent answers from its own conversation.
  2. Runners. Tool calls run on a machine you choose, in a folder you choose, with that machine's logins, and the agent knows that folder's AGENTS.md and skills as pi would.
  3. Models of your choice. Any model pi can name, named the way pi names it.
  4. Stable messaging. A message between threads arrives once and its answer comes back once, even across restarts and stops.
  5. Forks. Fork a thread at any message, with each agent in it, to try another path from the same point.
  6. Memory (under exploration). A thread never has to end, and anything said in it can be found again, word for word.

A change serves one of these, or it doesn't land. The code is the truth, and examples/ shows each idea working.

The words

One word per thing. The test for a word: it names something you can point at in the code or the API, and nothing else in the list overlaps it. Under each, the words people reach for instead, and what they map to here.

Server built
The one process you start, npx github:oskarrough/agent-ide, on any box you own. It lends the folder it starts in as its first runner. It keeps every thread and every agent's conversation in one SQLite file, and Pi Durable makes sure a restart or a stop loses and repeats nothing. What you might call a workspace, or the cloud. A server is the workspace: one server is one world; run another for another.
Runner built
A program on a machine that lends the server two things: a folder and the model logins pi has there. Started by hand, or installed with one line, curl -fsSL <server>/connect-runner | sh, after which it keeps itself up to date. It can be read-only, and it can have an owner. What you might call a machine, a computer or a daemon. A machine is where runners run, one per folder if you like, and a cloud sandbox is just another machine. The daemon is the runner.
Agent built
A model, how hard it thinks, and the runner it runs on: sonnet:high@laptop. In each thread an agent has its own conversation. It is handed messages, posts only its final answer, and can read any agent's work: the tool calls it made and what they printed. It knows its folder the way pi does there: AGENTS.md and skills. Not a bot. An agent has no name of its own and no character; it is "this model, this hard, there".
Thread built
A conversation on the server, with any number of people and agents in it. A message asks the agents in its to, or whoever the thread asked last. Threads fork at any message, and talk to each other: an answer comes back to the thread that asked exactly once. Threads don't live on runners. A thread can ask an agent on the laptop and one on the vps side by side.
Client built
Whatever you look through: the web client in any browser, the CLI in a terminal, a Matrix room. They all speak the same small HTTP and WebSocket API, and none of them stores anything. What you might call the desktop or the mobile app: npx github:oskarrough/agent-ide in a folder and a browser tab, on your laptop or, over Tailscale, your phone.
Bot later
A who: a name and instructions, running as some agent. ada might be sonnet:high@laptop plus her character; move her to the vps and she's still ada. It belongs on the server, because it's part of the thinking, not the doing. Waits until everything above is rock solid.

Each part is optional and falls back to pi's defaults on that runner: laptop alone is its default model. The model part is anything pi --model takes, resolved by pi on the runner.

The machine

flowchart TB
  clients["client.html and cli.js, anywhere"] -- "HTTP and /ws" --> server["server.js: one Pi Durable harness, threads, every agent's loop, one SQLite file; checks each runner's owner"]
  runner["runner.js on laptop: stores nothing"] -- "dials /ws" --> server
  server -- "resolve, stream, files, exec, cancel" --> runner
  runner -. "file tools stay inside; $ commands only start here" .-> folder["~/code"]
  runner -- "pi logins" --> providers["Anthropic, OpenAI, …"]

The server thinks and the runner acts. Every agent's loop runs in the server; each model call and tool call crosses the socket the runner dialled, so its logins never leave its machine. File tools stay inside the runner's folder, but a command only starts there, which is why that line is dashed. A runner with an owner says whom it takes work from, and the server checks.

Pi Durable does the heavy lifting: storage, tasks, ordering, retries, restarts, stops and forks. agent-ide adds four things on top.

  • A thread is a Pi conversation that never runs a model. Every entry is a message with an author and a body. What agent-ide adds, like a title, a parent, read markers and the thread's agents, sits beside it as a Pi doc.
  • A runner lends the server a machine's pi logins and a folder, and stores nothing. The server registers it as a Pi model provider and as the execution environment of every conversation whose model runs on it. Calls to an offline runner wait for it.
  • An agent is a model on a runner, provider/id@runner, resolved the way pi --model resolves it. In each thread an agent answers from its own Pi conversation.
  • A task is Pi's. Deliver hands an agent its messages, Shell runs $ cmd on a runner, and Anchor owns an agent's conversation so that a stop reaches it.

One message, start to finish

  R->>M: with the laptop's login

  A->>R: bash: bun test, in ~/code

  A->>R: model request, and so on
  A-->>T: only its final answer
  T-->>You: live, as it lands

The brain never leaves the server: the agent's loop, its conversation and its memory. The runner is its hands and its voice: it runs the tools, and it carries the model calls on its own logins. If the runner drops mid-way, the agent waits for it and carries on.

Principles

Messages

  • Agents are handed messages, and can look up anything. Each delivery hands an agent everything it hasn't seen yet as one input, and only its final answer comes back to the thread. Its tool calls stay in its own conversation, where any agent can read them with threads.
  • A message asks the agents in its to. With no to, it asks whoever the thread asked last, and to: null asks nobody.
  • Threads talk like email. An agent asks with post: with no thread, a new child that holds only the question, for a side question; to a thread, whoever is there, with all they know there. The answer goes back to the asking thread, and a reply to that answer ends the exchange.
  • Posting to a thread that asked you something answers it, so a progress note mid-work comes back once and goes no further.
  • A name is one line of plain text and a message's later lines are indented, so nobody can forge a speaker in an agent's input. Agents are marked as agents by what they wrote, never by their name: a person's message is an instruction, an agent's is a colleague's report or request.
  • The client watches Pi's own event streams, so replies and tool calls show live. A reconnect starts from fresh snapshots.

Durability

  • Every write lands in the commit that ends or advances a Pi task, so a restart repeats nothing. A retried request with the same requestId gets the first result back.
  • A stop posts nothing, and messages that were never delivered wait for the next delivery.
  • A fork forks the thread and each agent's conversation at the same point, in one commit.

Runners

  • Whoever lends a runner pays for the thinking on it: its pi logins are its agents' logins, and the server holds none. A shared pool is a runner without an owner.
  • A runner with an --owner takes work only from its owner and the names it --allows: people, or @runner for the agents there. An agent always reaches its own runner. Allowing is transitive: allow @desktop, and whoever desktop takes can reach you through its agents. A refusal writes nothing. Agents can't pick their name, but a person can claim to be the owner.
  • A runner started --read-only lends its folder to read: writes and commands come back as errors.

A runner's life

stateDiagram-v2
  direction LR
  [*] --> Online: curl …/connect-runner | sh
  Online --> Offline: machine sleeps, network drops
  Offline --> Online: dials back by itself
  Online --> Updating: new runner on the server, and it's idle
  Updating --> Online: fetched, installed, restarted

The server ships its own runner, so a runner always matches its server. It never updates mid-answer: the server asks only when it has nothing open.

Modules

Anything optional is a module: one file, switched by an env var of the same name.

talk.js on
Gives agents post and threads tools: start or answer other threads, and read any thread or any agent's work.
status.js on
Has runners report status to their terminal.
context.js on
Gives each agent what pi reads in its folder, AGENTS.md and the skills, found by pi on the runner before every request.
director.js off
Asks the agents a message @mentions.
memory.js off
Gives each thread a memory of short lines that agents read within their context and zoom back down to the words.
search.js off
Gives agents web_search, through Exa's free search.
matrix.js off
Mirrors Matrix rooms into threads, and its top says how to set it up.

Decided

Who pays: the runner

An agent's model calls go out through the pi logins on its runner, so whoever lends a runner pays for the thinking on it. agent-ide is for one person and for teams alike, and this answer holds for both.

flowchart LR
  subgraph yours["Your runner pays for your agents"]
    a1["sonnet@laptop"] -- "thinks with" --> l1["the laptop's login"]
    a1 -- "works in" --> f1["the laptop's ~/code"]
  end
  subgraph pool["A shared pool is a runner without an owner"]
    a2["anyone's agent @pool"] -- "thinks with" --> l2["a key in that machine's environment"]
    a2 -- "works in" --> f2["its folder"]
  end
  • Just you: every runner is yours, with your logins. Nothing to decide.
  • A team: Ana's runners pay for the agents on them, and --owner and --allow say who else may use them. Nobody's subscription quietly becomes everyone's, and someone who leaves takes their logins along by stopping their runner.
  • A pool, if a team wants one: a runner without an owner, next to the server, with a key in its environment. pi's enabled models there are the list, and pi's default there is the default.

Two costs we accept: a machine with no login needs a key in its environment, and each machine needs pi and /login once. Thinking on one runner while working on another would be one optional field, if it's ever needed.

The whole picture lives in the thread

When work spans machines, an agent on each one does its part, and any agent can read another's work with threads {thread, agent}: not only what it said, but the tool calls it made and what they printed, word for word. Every hop stays a message you can read, and nobody works from a summary. So each agent keeps one runner; for more reach, its bash has ssh.

sequenceDiagram
  participant You
  participant L as sonnet@laptop
  participant V as sonnet@vps, in a child thread
  You->>L: the site throws 500s, fix it
  L->>V: post: what's failing on the vps?

  V-->>L: a null user in /api/me
  L->>V: threads: read sonnet@vps's work

  L->>L: edit and test, in ~/code
  L-->>You: fixed, and why
  • Agents are handed messages, and can look up anything.
  • Any agent may read any agent's work, as any person already can through the API.
  • Long output is cut at 4,000 characters, saying how much is left; query finds the part that matters.

Open

Nothing right now. Bots come here when we start on them.

Where we are

  • A server that survives restarts and stops, on Pi Durable.
  • Runners: started by hand or with one curl line, self-updating, read-only if you like, with owners.
  • Agents as model:thinking@runner, knowing their folder's AGENTS.md and skills.
  • Threads with many people and agents, forks, and threads that talk to each other.
  • Clients: the web client, the CLI, Matrix.
  • Agents read each other's work, so work across machines stays in the thread.
  • Web search, as a module: the simplest that works, to show how a tool plugs in.
  • Bots, once the rest is rock solid.
  • Memory, a thread that never has to end, still being explored.
  • A desktop app, a phone app, cloud machine kinds, accounts. Each is a shell around what's already here.

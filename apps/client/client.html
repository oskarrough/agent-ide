agent-ide

Why use this over ChatGPT, Claude, T3 and the rest? Maybe you wouldn't. I do, because I like being able to change absolutely everything.

agent-ide is a minimal, stable base for building on AI. It's the chat app you know, with many threads and any model you like, plus a few things on top:

  1. Threads with many authors. You, friends and agents talk in one thread, and each agent can be any model pi can name, named the way pi names it.
  2. Runners. Tools run on a machine and in a folder you choose, with that machine's logins, and the agent knows that folder's AGENTS.md and skills.
  3. Threads that talk. An agent asks another thread, and the answer comes back once, even across restarts and stops.
  4. Forks. Start a new thread from any message, with the same agents.
  5. Stays on. A restart or a stop loses nothing.

It runs on your own computer, with nothing third-party except the model. Bots, @mentions, Matrix rooms, memory and search are modules you switch on, or write yourself. About five thousand lines: fork it, point your AI at it, change it.

The rest of this page walks you through it, then says what it's made of.

Hello, Agent IDE

Start it where it can stay on.

npx github:oskarrough/agent-ide

Lend it your laptop

Now an agent can work on the server's own machine. To have it work on your laptop instead, run this there. Your laptop dials the server, so it has to reach it: the same network, or Tailscale. 


		


		

			
Where the work happens

			

				The agents run on the server, their tools on the runner. Each tool the agent calls travels
				down its wire and runs in the runner's folder, with the runner's logins.
			

			

				
			

		


		

			
Ask two at once

			

				Click a runner to ask it. Shift-click another to ask it too. One message, two agents, each
				answering from its own machine. With one runner, two of its models answer side by side.
			

			

				
			

		


		

			
Agents talk to each other

			

				An agent asks another with its post tool. With no thread, it starts a child
				that holds just the question. Given a thread, it asks whoever is there, with everything they
				already know there.
			

			

				The answer comes back once, as a card, and wakes whoever asked. Nothing else crosses: what's
				said in a child stays in the child. And an agent's words reach others marked as an agent's,
				so none can pass for yours.
			

			

				
			

		


		

			
Pull the plug

			

				Ask something slow. While its wire is green, stop the server where it runs, with
				Ctrl-C, and start it again. The server goes dashed, then green, and the answer
				lands, once. A command that was running when the plug came out is cut off, and the agent
				says so: it picks up where Pi left it, not where the shell was.
			

			

			

				This page keeps nothing itself. Close the tab, or the laptop, and nothing is lost either.
			

		


		

			
Fork

			

				Wish you'd asked differently? Hover any message for its fork. A new thread starts
				from there, with the same agents, each remembering only what came before it. The two sit
				side by side, linked both ways.
			

			

				
			

		


		

			
Bring a friend

			

				A thread isn't yours alone. Send someone the link and they're in it, writing next to you and
				your agents.
			

			

				
			

			

				There are no accounts: a name is whatever you say it is. Keep the server on a network you
				trust.
			

		


		

			
Memory

			

				A thread that never has to end. Each message gets one short line, pairs of lines merge into
				one going up, and an agent reads those lines instead of every word. When it needs the words,
				it zooms back down. Click a line to do the same.
			

			

				Load a thread of three people building a shed: 32 messages, where the gate code and the
				colour change halfway. Watch the lines get written, from the messages up. Then ask an agent
				what's true now.

The words

			

				One word per thing. The test for a word: it names something you can point at in the code or
				the API, and nothing else in the list overlaps it. Under each, the words people reach for
				instead, and what they map to here.
			


			

				
Server

				

					The one process you start,
					npx github:oskarrough/agent-ide, on any box you own. It lends the folder it
					starts in as its first runner, and keeps every thread and every agent's conversation in
					one SQLite file.
					What you might call a workspace, or the cloud. One server is one world.
				


				
Runner

				

					A program on a machine that lends the server two things: a folder and the model logins pi
					has there. Started by hand, or installed with one line,
					curl -fsSL <server>/connect-runner | sh.
					What you might call a machine, a computer or a daemon. A machine is where runners run,
						one per folder if you like, and a cloud sandbox is just another machine.
				


				
Agent

				

					A model, how hard it thinks, and the runner it runs on:
					sonnet:high@laptop. In each thread an agent has its own conversation, and
					knows its folder the way pi does there: AGENTS.md and skills. Its name in the thread is
					sonnet@laptop, unless you give it another, as
					reviewer=sonnet@laptop, so two of one model can work side by side. In its
					thread the name reaches it; from anywhere, 12/reviewer does. A fork keeps the
					names.
					Not a bot. A name is not a character; the agent is "this model, this hard,
						there".
				


				
Thread

				

					A conversation on the server, with any number of people and agents in it.
					Threads don't live on runners. A thread can ask an agent on the laptop and one on the
						vps side by side.
				


				
Client

				

					Whatever you look through: the web client in any browser, the CLI in a terminal, a Matrix
					room. They all speak the same small HTTP and WebSocket API, and none of them stores
					anything.
					What you might call the desktop or the mobile app: a browser tab, on your laptop or,
						over Tailscale, your phone.
				

			


			
How an agent is named

			

				sonnetmodel:highthinking@laptoprunner
			

			

				Each part is optional and falls back to pi's defaults on that runner:
				laptop alone is its default model. The model part is anything
				pi --model takes, resolved by pi on the runner.
			


			
The machine

			
flowchart TB
  clients["client.html and cli.js, anywhere"] -- "HTTP and /ws" --> server["server.js: one Pi Durable harness, threads, every agent's loop, one SQLite file; checks each runner's owner"]
  runner["runner.js on laptop: stores nothing"] -- "dials /ws" --> server
  server -- "resolve, stream, files, exec, cancel" --> runner
  runner -. "file tools stay inside; $ commands only start here" .-> folder["~/code"]
  runner -- "pi logins" --> providers["Anthropic, OpenAI, …"]


			

				Pi is the harness: its prompt, tools and loop. The server runs it for every agent, and the
				tools run on a runner. Each model call and tool call crosses the socket the runner dialled,
				so its logins never leave its machine. File tools stay inside the runner's folder, but a
				command only starts there, which is why that line is dashed.
			

			

				Pi Durable does the heavy lifting: storage, tasks, ordering, retries, restarts, stops and
				forks. agent-ide adds three things on top.
			

			
    
				
  • 
					A thread is a Pi conversation that never runs a model. Every entry is a message
					with an author and a body. What agent-ide adds, like a title, a parent, read markers and
					the thread's agents, sits beside it as a Pi doc.
				
    • 
				
  • 
					A runner is, to the server, a Pi model provider and the execution environment of
					every conversation whose model runs on it. Calls to an offline runner wait for it.
				
    • 
				
  • 
					A task is Pi's. Deliver hands an agent its messages, Shell runs
					$ cmd on a runner, and Anchor owns an agent's conversation so that a stop
					reaches it.
				
    • 
			


			
One message, start to finish

			
sequenceDiagram
  participant You as You, in any client
  participant T as Thread, on the server
  participant A as The agent, on the server
  participant R as runner laptop
  participant M as The model's provider
  You->>T: "fix the flaky test", to sonnet:high@laptop
  T->>A: everything it hasn't seen yet, as one input
  A->>R: model request
  R->>M: with the laptop's login
  M-->>A: streamed back: call bash
  A->>R: bash: bun test, in ~/code
  R-->>A: what it printed
  A->>R: model request, and so on
  A-->>T: only its final answer
  T-->>You: live, as it lands


			
If the runner drops mid-way, the agent waits for it and carries on.


			
Principles

			
Messages

			
    
				
  • 
					Agents are handed messages, and can look up anything. Each delivery hands an agent
					everything it hasn't seen yet as one input, and only its final answer comes back to the
					thread. Its tool calls stay in its own conversation, where any agent can read them with
					threads, as any person can through the API. Long output is cut at 4,000
					characters, saying how much is left; query finds the part that matters.
				
    • 
				
  • 
					A message asks the agents in its to. With no to, it asks whoever
					the thread asked last, and to: null asks nobody.
				
    • 
				
  • 
					Threads talk like email. An agent asks with post. With no thread, it starts a
					child that holds only the question, for a side question. Given a thread, it asks whoever
					is there, with all they know there. The answer goes back to the asking thread, and a reply
					to that answer ends the exchange. Nothing else crosses: what's said in a child stays in
					the child.
				
    • 
				
  • 
					Posting to a thread that asked you something answers it, so a progress note mid-work comes
					back once and goes no further.
				
    • 
				
  • 
					A name is one line of plain text and a message's later lines are indented, so nobody can
					forge a speaker in an agent's input. Agents are marked as agents by what they wrote, never
					by their name: a person's message is an instruction, an agent's is a colleague's report or
					request.
				
    • 
				
  • 
					The client watches Pi's own event streams, so replies and tool calls show live. A
					reconnect starts from fresh snapshots.
				
    • 
			

			
Durability

			
    
				
  • 
					Every write lands in the commit that ends or advances a Pi task, so a restart repeats
					nothing. A retried request with the same
					requestId gets the first result back.
				
    • 
				
  • 
					A stop posts nothing, and messages that were never delivered wait for the next delivery.
				
    • 
				
  • 
					A fork forks the thread and each agent's conversation at the same point, in one commit.
				
    • 
			

			
Runners

			
    
				
  • 
					A runner with an --owner takes work only from its owner and the names it
					--allows: people, or @runner for the agents there. An agent
					always reaches its own runner. Allowing is transitive: allow @desktop, and
					whoever desktop takes can reach you through its agents. A refusal writes nothing. Agents
					can't pick their name, but a person can claim to be the owner.
				
    • 
				
  • 
					A runner started --read-only lends its folder to read: writes and commands
					come back as errors.
				
    • 
				
  • 
					A runner shows its key when it dials in, so nobody can take its name. The server mints a
					key per runner and keeps only its hash; a new key cuts off the old one. Revoking takes the
					key away: the runner goes offline and stops dialling back. People have no keys yet, so
					anyone who can reach the server can mint one.
				
    • 
			


			
A runner's life

			
stateDiagram-v2
  direction LR
  [*] --> Online: curl …/connect-runner | sh, with its key
  Online --> Offline: machine sleeps, network drops
  Offline --> Online: dials back by itself
  Online --> Revoked: its key is taken away
  Revoked --> [*]
  Online --> Updating: new runner on the server, and it's idle
  Updating --> Online: fetched, installed, restarted


			

				The server ships its own runner, so a runner always matches its server. It never updates
				mid-answer: the server asks only when it has nothing open.
			


			
Modules

			

				Anything optional is a module: one file. They're picked the way Pi picks tools, in
				agent-ide.json or MODULES=+search,-talk: names replace the
				defaults, +name and -name change them, and a path is a module of
				your own.
			

			

				
talk.js on

				

					Gives agents post and threads tools: start or answer other
					threads, and read any thread or any agent's work.
				

				
status.js on

				
Has runners report status to their terminal.

				
context.js on

				

					Gives each agent what pi reads in its folder, AGENTS.md and the skills, found by pi on the
					runner before every request.
				

				
director.js off

				
Asks the agents a message @mentions by name.

				
memory.js off

				

					Gives each thread a memory of short lines that agents read within their context and zoom
					back down to the words.
				

				
search.js off

				
Gives agents web_search, through Exa's free search.

				
matrix.js off

				
Mirrors Matrix rooms into threads, and its top says how to set it up.

				
bots.js off

				

					One name in many threads: a name with a home thread, a recipe and instructions. Ask
					ada in any thread and an agent named ada joins it from her recipe;
					ada=haiku@desk gives that thread another model. Every ada reads her
					instructions before each request and knows her other threads and the other bots, so she's
					one person, not one conversation. At home she rewrites them herself, or makes another bot.
					Forgetting her keeps every thread.
				

			


			
Who pays: the runner

			

				An agent's model calls go out through the pi logins on its runner, so whoever lends a runner
				pays for the thinking on it, and the server holds no logins.
			

			
flowchart LR
  subgraph yours["Your runner pays for your agents"]
    a1["sonnet@laptop"] -- "thinks with" --> l1["the laptop's login"]
    a1 -- "works in" --> f1["the laptop's ~/code"]
  end
  subgraph pool["A shared pool is a runner without an owner"]
    a2["anyone's agent @pool"] -- "thinks with" --> l2["a key in that machine's environment"]
    a2 -- "works in" --> f2["its folder"]
  end


			
    
				
  • Just you: every runner is yours, with your logins. Nothing to decide.
    • 
				
  • 
					A team: Ana's runners pay for the agents on them. Nobody's subscription quietly
					becomes everyone's, and someone who leaves takes their logins along by stopping their
					runner.
				
    • 
				
  • 
					A shared pool, if a team wants one: a runner without an owner, next to the server,
					with a key in its environment. pi's enabled models there are the list, and pi's default
					there is the default.
				
    • 
			

			

				Two costs we accept: a machine with no login needs a key in its environment, and each
				machine needs pi and /login once. Thinking on one runner while
				working on another would be one optional field, if it's ever needed.
			


			
The whole picture lives in the thread

			

				When work spans machines, an agent on each one does its part, and any agent can read
				another's work with threads {thread, agent}, word for word. Every hop stays a
				message you can read, and nobody works from a summary. So each agent keeps one runner; for
				more reach, its bash has ssh.
